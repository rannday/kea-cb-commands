# Upstream feasibility investigation

Investigated 2026-10-14 against public upstream tags `Kea-3.2.1` and `Kea-3.0.4`.
Links below pin source to a release rather than the development branch. Only
public open-source implementation and public documentation were examined. No
proprietary hook source or binaries were obtained or inspected.

## Finding and evidence boundary

**A standalone command hook is verified through native PostgreSQL and MariaDB
subnet reads and minimal subnet create/update on Kea 3.2.1.** See the current
[Milestone 4 verification record](development.md#milestone-4-verification-record).
The backend manager header explicitly describes singleton access by command hook
libraries. Public installed interfaces expose backend reads and writes. Upstream
builds `kea-dhcpsrv` as a shared library. There is no apparent requirement to patch
Kea or write SQL independently.

In the initial diagnostic milestone, the hook was compiled, linked, and loaded into an unmodified Kea 3.2.1
DHCPv4 build in Debian WSL. It successfully resolved the manager/pool and passed
command, unload/reload, and shutdown checks in both threading modes. Dynamic
symbol inspection confirmed the manager accessor and both families' subnet write
wrappers in the built shared `kea-dhcpsrv`. No SQL operation was executed. This
does not establish SQL behavior, installed-package completeness, DHCPv6 runtime
compatibility, or compatibility with 3.0.4. See the
[verification record](development.md#initialization-verification-record).

## Release and language baseline

The [ISC release table](https://www.isc.org/kea/) lists 3.2.1 as current stable
(September 2026, maintenance through July 2027), 3.0.4 as stable LTS (July 2026,
maintenance through June 2028), and 3.3.2 as development. Initial build candidates
are 3.2.1 first and 3.0.4 second. Do not imply support for every 3.x release or
older 2.x installations from these two source reviews.

The pinned [3.2.1 Meson build](https://github.com/isc-projects/kea/blob/Kea-3.2.1/meson.build)
(`cpp_standard` checks near line 397) requires at least C++11, recommends C++14,
and can require C++20 for optional Botan 3/NETCONF dependencies. The
[3.0.4 build](https://github.com/isc-projects/kea/blob/Kea-3.0.4/meson.build)
has the same basic policy. The [installation documentation](https://kea.readthedocs.io/en/kea-3.2.1/arm/install.html)
describes a C++14-capable compiler. This project defaults to C++14 and selects
OpenSSL for the reproducible upstream build. Override the standard to match the
actual Kea build when required; compiler, standard library ABI, Boost, and build
options matter independently of the language standard.

`kea-process`, `kea-cc`, `kea-log` and their transitive dependencies. The upstream

## Hook and command lifecycle

[`LibraryHandle::registerCommandCallout`](https://github.com/isc-projects/kea/blob/Kea-3.2.1/src/lib/hooks/library_handle.h)
registers native commands. The public
[`stat_cmds` entry points](https://github.com/isc-projects/kea/blob/Kea-3.2.1/src/hooks/dhcp/stat_cmds/stat_cmds_callouts.cc)
demonstrate process/family checking, registration in `load`, logging, `unload`, and
the multi-threading declaration.

[`HookedCommandMgr`](https://github.com/isc-projects/kea/blob/Kea-3.2.1/src/lib/config/hooked_command_mgr.cc)
passes `command` and `response` as `isc::data::ConstElementPtr` callout arguments.
It also adds registered hook commands to `list-commands`.
[`createAnswer`](https://github.com/isc-projects/kea/blob/Kea-3.2.1/src/lib/cc/command_interpreter.h)
constructs native `result`, `text`, and `arguments` responses.

[`LibraryManager`](https://github.com/isc-projects/kea/blob/Kea-3.2.1/src/lib/hooks/library_manager.cc)
uses `dlopen` with `RTLD_NOW | RTLD_LOCAL`, looks up `version`, verifies its exact
hook API version, checks threading compatibility, and invokes initialization.
Teardown removes registered callouts and unloads the library. This project exports
`version`, `load`, `unload`, and `multi_threading_compatible` with C linkage and
default symbol visibility; implementation symbols are hidden.

The [3.2.1 hook header](https://github.com/isc-projects/kea/blob/Kea-3.2.1/src/lib/hooks/hooks.h#L16)
defines `KEA_HOOKS_VERSION` as `30201`; [3.0.4](https://github.com/isc-projects/kea/blob/Kea-3.0.4/src/lib/hooks/hooks.h#L16)
defines `30004`. It changes even between patch releases. The same header explains
why statically linked Kea cannot provide the correct singleton objects to external
hooks. Only shared-library Kea is in scope here. A matching integer is necessary
but does not prove C++ ABI compatibility. Never reuse one artifact across the two
targets, mix headers and runtime packages, or embed static Kea archives.

## Backend initialization and selectors

The open-source backend hook entry points
([MySQL](https://github.com/isc-projects/kea/blob/Kea-3.2.1/src/hooks/dhcp/mysql/mysql_callouts.cc),
[PostgreSQL](https://github.com/isc-projects/kea/blob/Kea-3.2.1/src/hooks/dhcp/pgsql/pgsql_callouts.cc))
register backend factories. Their shared modules are `libdhcp_mysql.so` and
`libdhcp_pgsql.so` in this release (see the corresponding
[MySQL build](https://github.com/isc-projects/kea/blob/Kea-3.2.1/src/hooks/dhcp/mysql/meson.build)
and [PostgreSQL build](https://github.com/isc-projects/kea/blob/Kea-3.2.1/src/hooks/dhcp/pgsql/meson.build)). Kea's
[`CBControlBase::databaseConfigConnect`](https://github.com/isc-projects/kea/blob/Kea-3.2.1/src/lib/process/cb_ctl_base.h#L133)
disconnects the previous pool and uses the manager's `addBackend` with configured
database access parameters. Load the required open-source SQL hook and configure
`config-control` through Kea itself. The diagnostic needs neither a SQL hook nor
database credentials, and must not initialize databases on its own.

[`BackendSelector`](https://github.com/isc-projects/kea/blob/Kea-3.2.1/src/lib/database/backend_selector.h)
identifies backend type, host, and port; it is distinct from a server selector.
[`BaseConfigBackendPool::createUpdateDeleteProperty`](https://github.com/isc-projects/kea/blob/Kea-3.2.1/src/lib/config_backend/base_config_backend_pool.h#L487)
requires **exactly one selected backend**, throwing `NoSuchDatabase` or
`AmbiguousDatabase` otherwise. A backend selector does not offer an arbitrary
database-name discriminator, so some multi-database configurations need an
explicit ambiguity policy. Do not broadcast writes by iterating private state.

[`ServerSelector`](https://github.com/isc-projects/kea/blob/Kea-3.2.1/src/lib/database/server_selector.h)
supports common/all, explicit tags, unassigned, and unrestricted selection modes;
their legality depends on the operation. `ALL` refers to common configuration,
not an instruction to fan out a mutation to every backend or tag. In
[`databaseConfigFetch`](https://github.com/isc-projects/kea/blob/Kea-3.2.1/src/lib/process/cb_ctl_base.h#L195),
an empty configured server tag selects `ALL`, otherwise `ONE(tag)`. Object
associations, common values, and tag overrides must follow each backend method's
contract. Command policy must validate selectors rather than infer them silently.

## Transactions, schema, and activation

The native subnet write implementations above create `MySqlTransaction` or
`PgSqlTransaction`, establish scoped audit revisions, and commit on success.
The transaction classes
([MySQL](https://github.com/isc-projects/kea/blob/Kea-3.2.1/src/lib/mysql/mysql_connection.h#L181),
[PostgreSQL](https://github.com/isc-projects/kea/blob/Kea-3.2.1/src/lib/pgsql/pgsql_connection.h#L140))
roll back uncommitted work on destruction. This does not establish a public batch
transaction spanning arbitrary pool operations. Do not promise atomic multi-command
updates or manually manipulate the connection behind a backend.

Backend constructors call `ensureSchemaVersion`
([MySQL](https://github.com/isc-projects/kea/blob/Kea-3.2.1/src/hooks/dhcp/mysql/mysql_cb_impl.cc#L69),
[PostgreSQL](https://github.com/isc-projects/kea/blob/Kea-3.2.1/src/hooks/dhcp/pgsql/pgsql_cb_impl.cc#L92)).
Use the exact installed release's `kea-admin` for schema initialization/upgrades;
the hook must not introduce migrations, independently hardcode a schema version,
or bypass upstream validation. PostgreSQL and MySQL/MariaDB need separate real
integration gates despite the shared C++ interface.

**SQL commit and live DHCP configuration activation are separate steps.**
[`CBControlBase`](https://github.com/isc-projects/kea/blob/Kea-3.2.1/src/lib/process/cb_ctl_base.h#L233)
fetches audit changes and applies database configuration. The native
[`config-backend-pull` handler](https://github.com/isc-projects/kea/blob/Kea-3.2.1/src/bin/dhcp4/ctrl_dhcp4_srv.cc#L1253)
runs on the main thread and requests an update fetch; periodic fetch is another
path. A successful write cannot be reported as active without verifying the
appropriate pull and effective configuration. A pull failure after commit does
not imply that SQL rolled back. Concurrent writers, audit timestamps, validation
failure, retries after connection loss, and safe activation require future policy
and integration tests. Do not directly patch `CfgMgr` to imitate activation.

## Packaging and command compatibility

Standard packages sometimes provide development files; for example
[`kea-dev` on Debian trixie](https://packages.debian.org/trixie/kea-dev) is 2.6.3,
which does not match the initial targets. A package name alone does not establish
that installed headers, `kea.pc`, shared libraries, SQL modules, and the daemon
are from the required build. Building upstream source is not an architectural
requirement if a matching complete development installation exists. An isolated
source build is the recommended initial reproducible dependency path.

The [public Configuration Backend Commands documentation](https://kea.readthedocs.io/en/kea-3.2.1/arm/hooks.html#libdhcp-cb-cmds-so-configuration-backend-commands)
describes the commercial command surface. Public APIs make implementing command
adapters for native configuration operations plausible. **Exact drop-in behavior
is not established**: JSON parsing/defaults, selector restrictions, error codes,
overwrite semantics, supported object families, and activation policy need a
per-command specification and tests. Do not load this project's future commands
alongside another library registering the same names. No commercial command names
are registered by the prototype.

## Unresolved proof obligations

Milestone 2 added a native PostgreSQL read command. Milestone 3 hardens its
single-backend policy, rejects incomplete shared-network serialization and
verifies complex data and native recovery. See
[its contract and limitations](postgresql.md) and the current
[verification record](development.md#milestone-3-verification-record) and
[source-level backend review](backend-behavior.md).
The diagnostic-only record above is historical.

The pinned implementation confirms:

- [`getAllSubnets4`](https://github.com/isc-projects/kea/blob/Kea-3.2.1/src/lib/dhcpsrv/config_backend_pool_dhcp4.cc#L40)
  delegates to the selected native backend. An explicit missing backend throws;
  collections use first-nonempty semantics, not a union
  ([pool implementation](https://github.com/isc-projects/kea/blob/Kea-3.2.1/src/lib/config_backend/base_config_backend_pool.h#L384)).
- [`tossNonMatchingElements`](https://github.com/isc-projects/kea/blob/Kea-3.2.1/src/hooks/dhcp/pgsql/pgsql_cb_impl.h#L772)
  implements universal and specific tag filtering. Missing individual objects
  return null, while collection reads return empty collections.
- [`Subnet4::toElement`](https://github.com/isc-projects/kea/blob/Kea-3.2.1/src/lib/dhcpsrv/subnet.cc#L785)
  provides native configuration serialization.
- The PostgreSQL hook's
  [threading declaration](https://github.com/isc-projects/kea/blob/Kea-3.2.1/src/hooks/dhcp/pgsql/pgsql_callouts.cc#L140)
  assumes main-thread calls. The DHCPv4
  [main loop](https://github.com/isc-projects/kea/blob/Kea-3.2.1/src/bin/dhcp4/dhcp4_srv.cc#L1224)
  polls command IO synchronously. Our command creates no worker or retained state.
- Native PostgreSQL errors can include sensitive details and upstream can log
  them itself; hook command boundaries must catch exceptions before Kea's generic
  command-manager fallback serializes exception text.

1. Repeat compilation, symbol/dependency inspection, and lifecycle tests on
   3.0.4. Verify matching installed development packages separately; current
   3.2.1 evidence uses upstream's uninstalled shared-library build tree.
2. Keep exact-release ABI and both-threading-mode lifecycle checks as release
   gates. Resolve any visibility/ABI blocker before adding writes.
3. PostgreSQL and MariaDB complex reads, recovery and multiple-backend policy
   pass on the matching 3.2.1 build. MariaDB retry exhaustion is also verified.
   Schema mismatch and Oracle MySQL runtime remain untested. Native MySQL
   write-statement preparation requires write grants even for reads; PostgreSQL's
   SELECT-only fixture passes. See [runtime results and prerequisites](mysql.md).
4. Milestone 4 establishes a deliberately minimal native `cb-subnet4-set` contract
   on both SQL engines: strict validation, one-operation rollback, native audit
   and timestamps, and activation separate from persistence. Independent-writer
   races remain unsupported because upstream exposes no transaction spanning
   preflight and write. See [the mutation contract](commands.md) and
   [native source evidence](backend-behavior.md#native-subnet-mutations).
5. Add DHCPv6 parity and regression coverage. The initial source review of 3.0.4
   does not replace compilation and runtime verification on that release.
